# prg-editor comment join — make Phase 4 output publishable

- **Date:** 2026-08-12
- **Status:** Approved (design); implementation pending
- **Target files:** `ghcp/plugins/pr-review-graph/` (agent contract, one new script, two builders, SKILL.md, tests, manifests)
- **Origin:** Issue 1 of the review on PR #3 (`ncksol/ai_tools`), verified independently before acceptance
- **Provenance note:** the plugin was generated by an outside tool and vendored in PR #3. It has no
  upstream repository, no git metadata and its `LICENSE` names the same author, so this repository is
  its home and fixes land here directly.

## 1. Problem statement

A conforming Phase 4 result cannot be published. `prg-editor.agent.md` documents a return shape
containing five fields per finding — `fingerprint`, `severity`, `confidence`, `location`, `comment` —
but both payload builders call `assertPublishable`, which throws unless
`finding.deduplication?.verdict === 'distinct'`. The documented editor output carries no
`deduplication` object, so the review graph fails at Phase 5 for both providers.

This is not a theoretical mismatch. The `unwrap()` helper in `build-github-review.mjs` and
`build-azure-threads.mjs` explicitly destructures `inlineFindings` and `summaryFindings` — precisely
the editor's envelope — so feeding editor output straight into a builder is a supported path. Nothing
in SKILL.md Phase 4 or Phase 5 describes an intervening merge step that would restore the missing
fields.

The defect survived because no test exercises that path. Every existing builder test feeds findings
returned by `applyDeduplication`, which attaches `deduplication` itself, so the envelope branch of
`unwrap()` is never covered.

## 2. Evidence

- `skills/review-pull-request/scripts/build-github-review.mjs`: `unwrap()` accepts an array,
  `{findings}`, or `[...inlineFindings, ...summaryFindings]`; `assertPublishable()` requires a
  64-character lowercase hex `fingerprint` and `deduplication.verdict === 'distinct'`.
- `skills/review-pull-request/scripts/build-azure-threads.mjs`: identical `unwrap()` and
  `assertPublishable()`.
- `skills/review-pull-request/references/finding.schema.json`: a finding is one flat object carrying
  `category`, `severity`, `confidence`, `title`, `problem`, `trigger`, `consequence`, `evidence`,
  `recommendation`, `location`, `verification`, plus optional `comment`, `deduplication` and
  `fingerprint`. The schema already models the intended shape.
- `skills/review-pull-request/scripts/lib.mjs`: `authorComment(finding)` returns `finding.comment`
  when present and otherwise composes prose from `title`, `problem`, `trigger` and `consequence`.
  Attaching `comment` to a finding is therefore the designed integration point.
- `agents/prg-deduplicator.agent.md` with `deduplicate-findings.mjs`: the deduplicator returns a thin
  result keyed by fingerprint and `applyDeduplication` joins it onto the authoritative findings. The
  agent never echoes a finding back.
- `agents/prg-editor.agent.md` line 17 instructs the agent to preserve severity, confidence, location,
  change-tracking data and fingerprint. `deduplication` is absent from that list and from the JSON
  example.
- Nothing outside `prg-editor.agent.md` and the two `unwrap()` helpers references `inlineFindings`,
  `summaryFindings` or the editor's `summary` string.

## 3. Design decisions

### 3.1 Join by fingerprint rather than widening the agent contract

Two approaches were considered.

**Prompt-only.** Rewrite the agent contract so the editor returns complete findings with `comment`
added. No code changes. Rejected: it requires a language model to echo roughly twelve fields per
finding, including a 64-character SHA-256 digest and nested `verification` and `deduplication`
objects. Each field is an opportunity to corrupt authoritative data, and a violation surfaces only at
publish time, after the operator has already approved a preview.

**Join by fingerprint (chosen).** The editor returns only what it authored — prose keyed by
fingerprint — and a deterministic script joins that prose onto the deduplicated findings. Authoritative
data never leaves the script, so it cannot be dropped or altered. This matches the established pattern
already used for `prg-deduplicator`, and it makes the agent contract smaller rather than larger.

### 3.2 Remove unread fields from the editor contract

`inlineFindings` and `summaryFindings` are advisory only: both builders recompute comment placement
themselves via `isChangedLine`, and `unwrap()` simply concatenates the two arrays. The editor's
`summary` string has no consumer at all — `buildGitHubReview` composes its own review body. Because the
contract is being rewritten regardless, these fields are removed rather than carried forward. Retaining
output that no consumer reads is what allowed the original mismatch to go unnoticed. The agent's
`description` frontmatter is updated to match its narrowed role.

### 3.3 Strict failure in both directions

A comment whose fingerprint is not in the deduplicated set is an invented finding and throws. A finding
that receives no comment also throws. The alternative for the second case is to let
`authorComment` fall back to auto-composed prose, but that publishes un-edited text without the
operator noticing — a silent quality regression. Throwing matches the skill's existing rule that a
missing agent result is incomplete rather than assumed acceptable. Both errors name the offending
fingerprints so the operator can retry the editor.

### 3.4 Harden the builder entry point

Once the editor stops emitting `inlineFindings` and `summaryFindings`, that branch of `unwrap()` is
dead, and worse than dead: raw editor output piped into a builder would match no branch and yield an
empty array, producing an empty review instead of an error. Removing the branch alone would preserve
that trap. `unwrap()` therefore throws on an unrecognised shape, converting a silent failure into a
clear one. This is in scope because the fix changes what flows into the builders.

## 4. Data flow

```
Phase 3   deduplicate-findings.mjs apply    →  DEDUPED_FINDINGS_JSON  {findings, suppressed, held, …}
Phase 4   prg-editor  (findings in)         →  EDITOR_COMMENTS_JSON   {comments:[{fingerprint, comment}]}
          apply-comments.mjs DEDUPED EDITOR →  FINAL_FINDINGS_JSON    [ complete findings, each + comment ]
Phase 5   build-github-review.mjs PACKET FINAL  →  review payload
          build-azure-threads.mjs PACKET FINAL  →  thread payloads
```

`FINAL_FINDINGS_JSON` is a plain array of complete findings, which the builders' existing array branch
already accepts. No builder CLI signature changes.

## 5. Component: `scripts/apply-comments.mjs`

Mirrors `deduplicate-findings.mjs` in structure and conventions: ES module, Node built-ins only,
importing shared helpers from `lib.mjs`, exporting a pure function and providing a CLI entry point
guarded by `isMain`.

- **Export:** `applyComments(deduplicated, editorOutput)` returning an array of findings.
- **CLI:** `apply-comments.mjs DEDUPED_FINDINGS_JSON EDITOR_COMMENTS_JSON FINAL_FINDINGS_JSON`.
- **Input tolerance:** accepts either the object written by `deduplicate-findings.mjs apply`, reading
  its `findings` array, or a bare array of findings.
- **Behaviour:** for each finding, attach the `comment` whose `fingerprint` matches. Findings are
  returned in their input order with all original fields intact; `comment` is the only field written,
  and an editor-supplied comment replaces any `comment` already present on the finding.
- **Errors:** throw when a supplied comment matches no finding, and throw when a finding receives no
  comment. A comment that is absent, not a string, or empty after trimming counts as not received,
  because `authorComment` would silently fall back to auto-composed prose. Both messages list the
  fingerprints involved.
- **Non-goals:** it does not reorder, filter, re-sort or re-classify findings, and it does not decide
  inline versus summary placement.

## 6. Agent contract: `agents/prg-editor.agent.md`

The return contract becomes:

```json
{
  "comments": [
    {
      "fingerprint": "64 lowercase hex characters",
      "comment": "Author-facing Markdown"
    }
  ]
}
```

Body changes:

- Replace the "Preserve severity, confidence, location, change tracking data, and fingerprint"
  instruction, which no longer applies, with an instruction to return the fingerprint exactly as
  received and to author nothing else.
- Remove the instruction to move cross-cutting findings into `summaryFindings`; placement is decided by
  the builders.
- State that a comment must be produced for every finding supplied.
- Retain the existing comment-quality rules: lead with the defect, state trigger and consequence, cite
  the smallest sufficient evidence, suggest a direction rather than a replacement implementation, keep
  a normal inline comment under 140 words, and use neutral language.
- Keep `tools: []`, which `validate-plugin.mjs` enforces.

## 7. SKILL.md

Phase 4 gains the join command immediately after the `prg-editor` dispatch:

```bash
node <SKILL_DIR>/scripts/apply-comments.mjs \
  <DEDUPED_FINDINGS_JSON> <EDITOR_COMMENTS_JSON> <FINAL_FINDINGS_JSON>
```

Phase 4 prose is updated to state that the editor returns comments keyed by fingerprint and that the
join step produces `FINAL_FINDINGS_JSON`, which Phase 5 already consumes by that name. The existing
sentence about preserving the fingerprint marker produced by the payload builders is retained. The file
must stay within the 500-line limit asserted by `validate-plugin.mjs`.

## 8. Tests

Added to `tests/plugin.test.mjs`, following the existing style of building a packet from a fixture and
driving the real functions:

1. **Join produces a publishable payload.** Deduplicated findings plus documented editor output pass
   through `applyComments` into `buildGitHubReview`; the resulting payload contains the edited comment
   text and the fingerprint marker. This is the direct regression test for the reported defect.
2. **Unknown fingerprint throws.** A comment whose fingerprint matches no finding is rejected.
3. **Missing comment throws.** A finding with no corresponding comment is rejected.
4. **Raw editor output into a builder throws.** Passing `{comments: [...]}` directly to
   `buildGitHubReview` produces a clear error rather than an empty review, covering the hardened
   `unwrap()`.

## 10. Acceptance criteria

1. `npm test` passes from `ghcp/plugins/pr-review-graph`, including the four new tests.
2. `npm run validate` passes from the same directory.
3. A test demonstrates documented `prg-editor` output reaching a GitHub review payload with the edited
   comment intact.
4. Passing raw editor output directly to a builder throws a clear error instead of producing an empty
   review.
5. No builder CLI signature changes; `build-github-review.mjs` and `build-azure-threads.mjs` each keep
   their three-argument form.
